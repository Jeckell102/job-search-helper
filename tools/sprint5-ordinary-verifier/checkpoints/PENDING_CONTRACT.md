# Proposed exact private pending interface

For coordinator review, before State or launcher wiring. The verifier takes a byte-pinned private JSON snapshot of one already admitted ordinary single-Company pending item. State marker ownership, DB reads and writes, publication precedence, and the local leased finisher stay with their assigned owners.

`ordinary-rippling-verification-pending-v1` has exactly `schema`, `owner`, `admission`, and `observation`.

- `owner`: `cycle_id`, `cycle_started_at`, `request_id`, `request_fingerprint`, `company_id`, `source_revision`, `company_source_sha256`, `store_binding_sha256`, `observation_generation`. `company_source_sha256` freezes the exact Company row identity including displayed company name. `store_binding_sha256` refers to the coordinator's frozen State/Jobs physical and workbook ownership witness. The prototype requires the ordinary Forterra identity and a positive observation generation.
- `admission`: `authority_url`, `configured_url`, `capability_id`, `capability_digest`, `mapping_digest`, `configuration_digest`, `matrix_digest`, `runtime_binding_sha256`. The caller freezes the ordinary runtime binding and exact matching qualification. The verifier validates these fields and treats their digests as identity pins, with live authority and State checks deferred to the owning local finisher.
- `observation`: the exact `rippling-tenant-mismatch-v1` payload assigned to the provider lane, with `configured_url`, `expected_slug`, `observed_slug`, `response_sha256`. The verifier independently validates both raw page-zero tenant fields and matches the raw response hash. The configured, observed, and independently established Forterra tenants must all be distinct. PDW is the required separate control.

An independently supplied private execution pin freezes the exact pending SHA-256, candidate replay pin, saved configured-response SHA-256, and the single run's absolute deadline and request budget. It is separate from the pending item, so this lane does not add evidence or deadlines to the State schema. The verifier builds evidence from the original authority, listings, details, rereads, and configured-response bytes. It accepts no prebuilt evidence receipt or trio of fact digests as evidence input.

Terminal dispositions `VERIFIED_MISMATCH`, `HOLD`, `TIMEOUT`, `BUDGET_EXHAUSTED`, and `CHANGED_INPUT` refer only to the verifier channel. Receipt includes the exact input identity, verifier/source pins, budget observations, and canonical evidence digest when verified. A repeat under an unchanged identity returns the same receipt with separate `REUSED` reporting. A corrupt, mismatched, or conflicting receipt fails closed. Work interrupted before publication can resume under the same pin and original deadline. The verifier acquires neither scraper nor writer lease and has no State, Jobs, Sheets, event, fact, release, repair-task, or outcome write API.

## Prototype one-attempt custody refinement

The private one-generation reservation is durable before the offline worker starts and reserves the full request allowance for that attempt. If restart sees a complete unchanged receipt, it reports `REUSED` and serves the original unchanged result even after the deadline. If restart sees a matching reservation with no receipt, it reports `INTERRUPTED` with terminal hold while within the deadline, or timeout when expired. It does not spend a second request allowance. `BUSY` reports a concurrent private attempt with no new receipt. The coordinator still owns any sanctioned successor policy. Private slot and evidence directories must be exact owned paths under `/tmp`, with private regular files, closed grammars and independent pins. Receipt checksum detects corruption inside that owned channel. A hostile same-UID writer or caller inventing its own private channel is outside this prototype's custody boundary and must not be trusted by the eventual finisher.
