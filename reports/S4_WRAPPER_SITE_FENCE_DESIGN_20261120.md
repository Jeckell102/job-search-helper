## Alternatives and limits

- **Host-controlled gate.** An independently administered mandatory file-access policy can deny opening/reading this exact script to every identified launch domain while allowing the distinct installer domain to measure and replace it. It must follow the canonical name across inode replacement, cover direct venv/interpreter starts and service starts, and survive controller death and manager restart. Prove coverage before relying on one. No such installed policy was established here. It could preserve the current 47-file installer if already available.
- **Existing interlocks.** Keep the systemd conditions for manager starts and restart dependencies. A direct interpreter does not consult them. The scraper bootstrap owns the scraper lease and checks the release marker, but the installed wrapper does not enter that bootstrap before binding. Removing the script's execute bit or placing it on a noexec mount does not prevent Python from reading it. Moving the token touches a credential and leaves earlier wrapper imports executable. [Scraper bootstrap](/tmp/jsh-s4-dispatch-binding-qa.i45G33KN/release_admission_bootstrap.py:244)
- **Authority boundary.** The filesystem fence proves that cooperative launches opening this exact pathname while absent cannot run its host code. It cannot revoke already-open code, stop an alternate checkout or explicit bytecode invocation, prevent an independent SQLite writer, or constrain a same-UID actor able to recreate the script or read the private bundle. The installed tools directory is user-owned. Bind each supported alternate launch to an enforceable owner-controlled hold or establish that its effective destinations are disjoint. A process census, advisory locks and an empty port are supporting observations. They cannot establish exclusive same-user authority. If a known same-store route lacks a fence, keep joint release on hold. No change to unrelated programs is needed to make the narrower canonical-path claim.
