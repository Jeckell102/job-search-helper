## Minimum enforceable boundary

For the observed canonical trees, the concrete host-controlled option is a **read-only bind mount of a dedicated empty administrator-owned directory over each exact alternate checkout root**, in the host mount namespace used by the actual launchers. Make the covering directory inaccessible to the launch account and host-control the mount lifecycle. This hides launcher scripts, package modules, copied console scripts, checkout-local environment and fallback scripts in one operation per tree. The underlying source, credential files, lock inodes and job stores keep their contents and metadata. No production path is a mount target. Verify first that the authorized production pilot has no required executable, config, credential or State path under the proposed covers.

Ordinary file locks still help drain known writers. The backup normally uses one writer lock. The copy divides ownership across scraper, writer and review-writeback locks, supports environment-selected State, and starts some writable constructors before those locks. Holding locks in the controller loses the leases on death. A restarted lock-holder has a reacquisition gap. Masking individual shell launchers would also miss the reviewer, copied console and module paths. A tree-level fence is the smallest common pathname boundary identified for these actual routes. It temporarily blocks reads from those alternate trees as well. An already enforced host access policy denying the same checkout paths to all identified launch accounts/domains would serve the same purpose.

## Install, pilot and restoration proof

1. The host owner inventories actual launch accounts, schedulers, process and mount namespaces, and known inherited path overrides. Privately resolve State/queue parents, worker and console import roots, and destination equality. Capture canonical checkout parent/target identities, original mounts and existing lock inodes. Pause known launch sources and complete a coordinated drain before the covers. Never seize, recreate or unlink an active application's lock.
2. Journal the exact mount intent and expected underlying and covering identities in private state outside all covered paths. After applying each cover verify actual mount ID, source, flags, parent and visibility from every supported launch context. Close or disposition pre-existing processes with imported code, open scripts/store descriptors, or working directories **inside** the covered tree; an overmount does not revoke those references. Recheck outstanding remote work and the drain after closure. A discrepancy keeps production held.
3. Demonstrate the canonical entry files cannot be opened by the real launch identity in those namespaces; use path-open/lookup probes and fixture tests, avoiding a live command that could fall through to another installation. For Python module/console routes also prove actual origin or that invocation is separately closed. A successful import from production or another editable installation is a separate route to evaluate. Covering the alternate tree alone does not deny that fallback. Verify that the approved production route can still select its pinned runtime.
4. The host fence outlives the source controller, wrapper restart and user-manager restart. Keep it through either installation or rollback, the manual pilot, and reconciliation of its durable outcome and delivery. If host reboot is within the operating window, require boot-persistent, fail-closed ordering before supported writers can start, or keep them disabled until an owner reattests the covers. A transient mount alone has no reboot guarantee. Restore only transaction-owned covers after checking their identity and confirming work is settled; verify the underlying original directories and control inodes reappear. An abnormal exit preserves the hold.

**Coverage limit.** A mount proves fresh lookup through the specific covered path in a verified namespace. A private namespace retaining the original mount, another bind alias, copied code, a pre-open interpreter, environment redirected to another installation, direct API/SQLite clients, remote users and manual workbook edits are outside that proof. Record a supported route individually as fenced, under the authorized production gate, or independently disjoint. An unresolved same-destination route prevents an exclusive pilot claim. Administrator authority and site-specific acceptance of these fences remain unverified. This review read local source, launcher metadata and the supplied preflight; it performed no activation or live destination check.
